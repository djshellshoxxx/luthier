# Codex Q1: real-time safety review

Reviewed `codex/luthier-qa-rtsafety` at `1a0805a679ac1677898bfd37d75fb9a52961058a` (2026-09-28). Scope: `PluginProcessor::processBlock/processSlice`, `LuthierEngine::processBlock/processSubBlock`, all `Source/DSP/**` files, and the relevant rhythm, parameter, MIDI and live helpers. This is a **static source review**. No live callback trace or Linux binary was available, so conditional risks below are not measured failures.

## Scope notes: file I/O, throws, denormals, reset and sample rates

- I found no direct file read/write in the ordinary `processBlock` call chain. Preset/guitar/IR loading, `BackingTrack::load`, and diagnostics export appear on other paths. `Source/PluginProcessor.cpp:2271-2277` explicitly defers bank-select preset loads to a timer. The part swap above is the major callback entry into structural work.
- `Source/Support/OutputNormalization.cpp:291-305` deliberately sleeps while waiting for calibration only if `isNonRealtime()` is true. This is an offline-render latency choice, not a live callback lock. A host misreporting real-time state would make it audible.
- The broad `noexcept` processing signatures do not prevent `std::bad_alloc`: a growing buffer within `noexcept` leads to termination. The confirmed callback growth sites are above. I did not identify an explicit `throw` in the reviewed DSP callback code.
- `Source/PluginProcessor.cpp:1220` installs `juce::ScopedNoDenormals`; recursive DSP commonly uses `sanitise/flushDenormal` (`Source/DSP/Common/DspCommon.h:49-65`). `Source/LuthierEngine.cpp:3030-3045` sanitises before the master, and `Source/DSP/Master/MasterBus.cpp:141-149` sanitises its input. This reduces but cannot prove absence of intermediate denormals or NaNs under invalid control inputs.
- `Source/LuthierEngine.cpp:147-270` resets string, effects, feedback, rhythm, tuning and display state; `Source/DSP/Effects/EffectsChain.cpp:37-49` resets pedal state. I did not identify a specific uninitialised reset field from this static pass. A determinism test comparing two reset/replay renders remains valuable, especially after a live part swap and a quality change.
- Sample-rate formulas generally use the prepared `sr`; several DSP types have default 44.1/48 kHz initializers. `Source/PluginProcessor.cpp:203-206` accepts the host rate without a finite/positive guard, while `Source/PluginProcessor.cpp:2120` divides by `currentSampleRate`; `Source/LuthierEngine.cpp:3063-3066` divides by `sr`. Hosts normally call `prepareToPlay` with a valid rate. Reject invalid values at the entry point and include 44.1/48/96/192 kHz and re-prepare tests.

## Verification and test handoff

The existing `Source/Tests/AudioThreadSafetyTests.cpp:203-282` counts same-thread allocations and blocking pthread locks during sparse 48 kHz, 128-sample playback after one warm-up block; it does not cover the triggers above. `CMakeLists.txt:209-219` would automatically include a new `Source/Tests/CodexQA_*.cpp`.

No new test file was added: the board requires a new test to build and run on Linux before handoff, and this execution environment has no local repository, JUCE checkout, CMake, Ninja or xvfb-run. The available `g++` alone cannot build this JUCE target. These findings were checked against exact source at the stated commit through the GitHub connector, but **Linux build and runtime tests are unverified**. Suggested first tests: (1) live part swap with both probes armed, (2) active strum/fingerpick while changing humanization, (3) secret effect enabled after warm-up, (4) oversized/dense MIDI, and (5) reset/replay and invalid-host-clock finite output. The P0 tests may intentionally fail until fixes land; do not turn them into a required green gate prematurely.

No production, spec, or shared helper files changed.
